# Spec 03

## Повний цикл тестування та мутаційний аналіз

## Context

### Current State

Реалізовано unit, PostgreSQL integration та process-level E2E тести на Vitest,
команду `make test` і звіт Stryker.

### Problem

Критичні сценарії потребували перевірки на рівнях unit, PostgreSQL та повного
API-процесу, а також аналізу якості тестів мутаційним тестуванням.

## Goal

Забезпечити повторювані тести критичних сценаріїв і обмежений мутаційний аналіз.

## Scope

### In scope

- Перевірка критичної бізнес-логіки unit-тестами та повне покриття логічних
  гілок `CarriersService`.
- Перевірка взаємодії з PostgreSQL і повних API-сценаріїв інтеграційними та
  E2E тестами.
- Єдиний повторюваний запуск тестів і обмежений мутаційний аналіз критичної
  логіки зі звітом про surviving mutants.

### Out of scope

- 100% покриття інших модулів, крім логічних гілок `CarriersService`.
- Мутаційний аналіз усієї кодової бази або встановлення мінімального score.
- Фінальний аудит «топ-3» без окремої команди користувача.

## Implementation

### Test organization and execution

- Unit `.spec.ts` розташовані поруч із класами; справжній `CarriersService`
  тестується з рукописними фейками залежностей, без реальної БД чи інших
  модулів. Синтетичні гілки декораторів та інструментування не враховуються.
- `tests/integration/` перевіряє repositories, транзакції/rollback,
  конкурентну купівлю й idempotency на справжній тестовій PostgreSQL.
- SQL-перевірки охоплюють ізоляцію власників і сесій, статуси заявок і квитків,
  видимість та пошук рейсів, а також область записів idempotency. Для списків
  перевіряються склад результатів, кількість і пагінація.
- `tests/e2e/` запускає зібраний застосунок окремим процесом і перевіряє HTTP
  сценарії зі справжньою тестовою PostgreSQL, зокрема відмови у доступі та
  видимість рейсів; smoke-перевірки збережені. Застосунок слухає динамічний
  порт, який повідомляє тесту через IPC; очікування запуску обмежене 30 с,
  а Vitest-таймаути сценаріїв і setup задані явно.
- `make test` чекає на готовність Compose PostgreSQL, мігрує `autobusua_test`
  із захистом від іншої БД, а потім послідовно запускає три набори. База не
  видаляється, явний cleanup тестових fixtures прибирає їхні записи; Vitest
  запускає тести серіалізовано. Автоматичний планувальник очищення idempotency
  вимкнений у тестових процесах; саме видалення перевіряється окремо на
  PostgreSQL у тимчасовій таблиці в транзакції, яку тест відкочує. Зовнішні
  процеси, підключені до тієї ж БД, тестовим набором не контролюються.

### Mutation testing

- `make mutation` запускає Stryker/Vitest для `AuthService`, `BookingsService`,
  `CarriersService` і `TripsService` лише з відповідними unit-тестами; score
  threshold не встановлено.
- [Звіт](../audits/03-mutation-testing-report.md) класифікує кожного мутанта:
  «реальна прогалина» порушує явний контракт; «еквівалентний» не змінює
  спостережувану поведінку; «прийнятний» може її змінювати, але лише у
  випадках, не заборонених явним контрактом, тому не обов'язково еквівалентний.
- Фінальний аудит після окремої команди виявив три прогалини в перевірках
  фільтрації та ізоляції списків; тести підсилено, результати наведено в
  [аудиті](../audits/03-testing-audit.md).
- Stryker не розширювався на SQL-репозиторії: цільові PostgreSQL та HTTP тести
  додатково перевірено окремими валідними ослабленнями SQL-предикатів.

## Acceptance Criteria

- **AC-1:** Unit-набір досягає 100% логічного branch coverage `CarriersService`,
  виключаючи синтетичні гілки декораторів та інструментування.
- **AC-2:** Integration-набір на справжній тестовій PostgreSQL перевіряє
  repositories, rollback, конкурентну купівлю останнього місця, idempotency
  replay та конфлікт для іншого payload.
- **AC-3:** E2E-набір запускає застосунок окремим процесом і проходить HTTP
  сценарій автентифікації, заявки й розгляду перевізника, створення/пошуку
  рейсу, купівлі/перегляду/скасування квитка та відмови неавторизованій ролі.
- **AC-4:** `make test` застосовує міграції до `autobusua_test` і запускає всі
  три рівні; тестова база залишається запущеною, а кожен тест прибирає лише
  створені ним записи.
- **AC-5:** `make mutation` запускає Stryker/Vitest лише для критичної
  бізнес-логіки з unit-тестами та створює звіт із класифікацією всіх surviving
  mutants за визначеннями цього документа.
- **AC-6:** Фінальний аудит із топ-3 ризиками пропущених дефектів не
  виконується без окремої команди користувача.

## Verification

- `make verify`: 85 unit, 24 integration і 4 E2E тести пройшли.
- E2E пройшли також із зайнятими колишніми портами 3100/3101 та із
  затримкою кожного запуску процесу на 6 с.
- Coverage `CarriersService`: 100% логічних гілок (10/10); попередній запуск
  mutation: 403 mutants, 349 killed, 54 survivors, класифікованих у звіті.
- Перевірки фільтра статусу квитків та ізоляції заявок і квитків за власником
  підсилено; відповідні тести падають при тимчасовому вимкненні SQL-фільтрів
  і проходять після відновлення SQL. Production-код не змінено.
- Додаткові перевірки SQL-фільтрів та HTTP-доступу пройшли; результати
  окремих негативних експериментів і їхні межі наведено в
  [аудиті](../audits/03-testing-audit.md).
- AC-4: test setup вимикає планувальник очищення; E2E дочірні застосунки та
  тестові міграції також отримують цей прапорець. Одноразовий production SQL
  очищення інтеграційно перевіряється на тимчасовій таблиці в rollback-транзакції;
  явне очищення fixtures видаляє лише записи тесту.
- `npm run typecheck`, `npm run lint` і `npm run format:check` пройшли.
- Додаткові перевірки — згідно з [verification checklist](../../standards/verification-checklist.md)
  та [Definition of Done](../../standards/definition-of-done.md).
