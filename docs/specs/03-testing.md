# Spec 03

## Повний цикл тестування та мутаційний аналіз

## Context

### Current State

Vitest і критичні тести вже додані, але всі набори поки що зібрані в корені
`tests/`. Поточний `make test` збирає застосунок і запускає Vitest; він ще не
піднімає Compose і не застосовує міграції до тестової БД. Наявний smoke-тест
запускає зібраний застосунок окремим процесом.

### Problem

Потрібно розділити перевірки логіки, PostgreSQL-взаємодії та наскрізної
поведінки API, а також перевірити критичну логіку мутаційним аналізом.

## Goal

Створити повторювані unit, integration та E2E тести на Vitest, що запускаються
через `make test`; додати окремий `make mutation` для Stryker.

## Scope

### In scope

- Unit-тести розміщуються біля тестованих класів у `.spec.ts`, як рекомендує
  [NestJS](https://docs.nestjs.com/fundamentals/testing).
- Unit-тести викликають справжній `CarriersService`; його залежності
  замінюються вручну написаними фейками, без запуску БД чи інших реальних
  модулів.
- `CarriersService` має 100% покриття логічних гілок; синтетичні гілки
  декораторів та інструментування не враховуються. `CarriersController`
  перевіряється E2E, а `CarriersRepository` — integration-тестами.
- Integration-тести містяться в `tests/integration/` та використовують
  справжню тестову PostgreSQL для repositories, транзакцій, rollback,
  конкурентності й idempotency.
- E2E-тести містяться в `tests/e2e/`, запускають зібраний застосунок окремим
  процесом і використовують HTTP та справжню тестову PostgreSQL.
- Наявні тести сортуються за рівнем: unit — біля класів, інші — у відповідних
  `tests/integration/` та `tests/e2e/` каталогах.
- `make test` піднімає Compose PostgreSQL, чекає на готовність, застосовує
  міграції до test database та запускає всі три рівні тестів.
- Команда залишає PostgreSQL запущеною й не очищає/пересоздає БД; тести
  прибирають лише записи, створені ними.
- `make mutation` запускає Stryker із Vitest runner лише для критичної
  бізнес-логіки, покритої unit-тестами; мінімального mutation score немає.
- Окремий звіт у `docs/audits/` класифікує кожного surviving mutant як
  «реальна прогалина», «еквівалентний» або «прийнятний» і пояснює класифікацію.
- Фінальний аудит тестів (топ-3 місця, де зелені тести можуть пропустити
  реальний дефект) виконується лише за окремою командою; виявлені прогалини
  усуваються посиленням тестів.

### Out of scope

- 100% покриття інших модулів, крім логічних гілок `CarriersService`.
- Підміна самого `CarriersService` unit-тестом або підняття реальної БД чи
  інших реальних модулів для його unit-тестів.
- Моки БД в integration/E2E тестах.
- Мутаційний аналіз усієї кодової бази або встановлення score threshold.
- Автоматичне видалення тестової БД, зупинка Compose чи фінальний аудит без
  окремої команди користувача.

## Acceptance Criteria

- **AC-1:** Branch coverage `CarriersService` дорівнює 100% логічних гілок,
  без синтетичних гілок декораторів та інструментування.
- **AC-2:** Unit-тест `.spec.ts` поруч із класом інстанціює справжній
  `CarriersService` із вручну написаними фейками залежностей, не піднімаючи
  реальну БД чи інші реальні модулі.
- **AC-3:** Vitest виявляє unit-файли `.spec.ts`, розміщені біля тестованих
  класів.
- **AC-4:** `tests/integration/` перевіряє repositories, транзакції та rollback
  на dedicated PostgreSQL, зокрема конкурентну купівлю останнього місця,
  idempotency replay і конфлікт для іншого payload.
- **AC-5:** `tests/e2e/` запускає застосунок окремим процесом і проходить HTTP
  сценарій автентифікації, заявки й розгляду перевізника, створення/пошуку
  рейсу, купівлі/перегляду/скасування квитка та відмови неавторизованій ролі.
- **AC-6:** Integration та E2E не замінюють PostgreSQL mock-ом; тестові сценарії
  використовують bootstrap-адміністратора й перевіряють рольові обмеження.
- **AC-7:** `make test` піднімає Compose, чекає готовності PostgreSQL, застосовує
  міграції до `autobusua_test` і запускає unit, integration та E2E.
- **AC-8:** `make test` відмовляється мігрувати або тестувати іншу БД, не
  видаляє тестову БД, залишає Compose запущеним і прибирає лише створені тестами
  записи після успішного чи невдалого сценарію.
- **AC-9:** `make mutation` використовує Stryker/Vitest лише для критичної
  бізнес-логіки з unit-тестами, без вимоги до мінімального score; звіт
  класифікує всіх surviving mutants, а «реальні прогалини» усуваються тестами.
- **AC-10:** Фінальний аудит із топ-3 ризиками пропущених дефектів не
  виконується без окремої команди користувача.

## Verification

- Запустити `make test` і перевірити послідовне виконання трьох рівнів на
  dedicated `autobusua_test`, включно з міграціями та відмовою для іншої БД.
- Перевірити, що unit-тест напряму використовує справжній `CarriersService` і
  рукописні фейки, без запуску БД чи реальних модулів.
- Перевірити branch coverage `CarriersService`, rollback, конкурентність,
  idempotency, bootstrap адміністратора, авторизацію та повний E2E-процес.
- Запустити `make mutation`; перевірити Stryker target, класифікувати survivors
  і повторити запуск після посилення тестів для реальних прогалин.
- Звірити результат із [verification checklist](../../standards/verification-checklist.md)
  та [Definition of Done](../../standards/definition-of-done.md).
- Фінальний аудит проводити лише після окремої команди.
