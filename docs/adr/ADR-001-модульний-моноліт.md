# ADR-001: Модульний моноліт

- Status: Accepted
- Date: 2026-11-16
- Deciders: Проєкт AutobusUA
- Technical area: Архітектура застосунку
- Related requirements: `docs/specs/01-foundation.md`
- Supersedes: N/A
- Superseded by: N/A

## Context and Problem Statement

AutobusUA має невеликий scope і не потребує незалежного масштабування окремих
частин або розподіленої команди. Потрібно визначити спосіб організації
backend, який збереже межі модулів без складності окремих сервісів.

## Decision Drivers

- Невеликий обсяг проєкту та одна команда.
- Просте локальне розгортання і тестування.
- Чіткі межі відповідальності модулів.
- Можливість подальшого розвитку без передчасної розподіленої інфраструктури.

## Considered Options

### Option 1: Модульний моноліт

- Переваги: один deployable-застосунок, прості транзакції та інтеграційні
  тести, модулі залишаються логічно ізольованими.
- Недоліки: незалежне масштабування модулів не передбачене.

### Option 2: Мікросервіси

- Переваги: незалежне розгортання і масштабування компонентів.
- Недоліки: мережеві виклики, складніша консистентність, спостережуваність,
  розгортання та тестування.

## Decision Outcome

Використовувати модульний моноліт NestJS з модулями `Auth`, `Carriers`,
`Trips` і `Bookings`. Модулі взаємодіють через внутрішні сервіси та контракти;
циклічні залежності заборонені.

## Positive Consequences

- Просте розгортання через один backend і Docker Compose.
- Транзакційні операції з рейсом і квитком виконуються в одній базі.
- Межі модулів визначені до початку реалізації.

## Negative Consequences

- Усі модулі масштабуються разом.
- Порушення меж модулів може створити сильне внутрішнє зв'язування.

## Risks and Mitigations

- Ризик розростання моноліту зменшується правилами залежностей і code review.
- За майбутньої потреби окремий модуль можна виділити в сервіс після появи
  вимірюваних причин для цього.

## Implications for Architecture

- Модулі: `Auth`, `Carriers`, `Trips`, `Bookings`.
- Дані: одна PostgreSQL-база.
- Інтеграції: внутрішні контракти замість мережевих викликів між модулями.
- Експлуатація: один deployable backend.

## Confirmation

Перевірити, що backend запускається як один застосунок, модулі мають окремі
межі, а перевірка залежностей не допускає циклічних імпортів.
