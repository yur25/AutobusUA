## Відповідність структурі специфікації

**Висновок:** фактична структура репозиторія загалом відповідає поділу та
обсягу, визначеним у Spec 02. HTTP-рівень, бізнес-логіка, доступ до даних і
спільна інфраструктура розділені. Поточна реалізація використовує PostgreSQL;
попередній in-memory етап був зафіксований окремо, а зовнішній HTTP API
збережений. Раніше виявлену проблему `make dev` виправлено, як описано нижче.

| Вимога специфікації | Фактична структура / реалізація | Оцінка |
|---|---|---|
| NestJS-модулі `Auth`, `Carriers`, `Trips`, `Bookings` | Окремі модулі в `src/modules/`; controllers обробляють HTTP, services містять сценарії, repositories виконують SQL | Відповідає |
| Спільні залежності, логування та обробка помилок | `src/common/`: DatabaseModule/Service, ALS-контекст, logger, idempotency, pagination та HTTP exception filter | Відповідає |
| PostgreSQL через `pg`, SQL у repositories і міграції | `pg` у залежностях, PostgreSQL repositories у відповідних модулях, `database/migrations/001-initial-schema.sql` | Відповідає |
| Перевірка підключення, pool lifecycle і локальне середовище | `DatabaseService` виконує `SELECT now()`, запускає міграції; Compose ізольовує сервіс на host port `55432` і створює окрему тестову БД | Відповідає |
| Транзакційність та ідемпотентність | Купівля, скасування, заявки, створення рейсів та їхні idempotency records обробляються транзакційно; у БД є відповідні унікальні обмеження | Відповідає |
| Мінімальна автоматизована перевірка | `tests/smoke-test.ts` перевіряє запуск, health/readiness, version і базовий список рейсів на `autobusua_test` | Відповідає узгодженому обмеженню |
| Makefile, документація й аудит | Команди Makefile, README, Spec 02, ER-діаграма, verification checklist і цей аудит | Відповідає; dev-запуск виправлено та перевірено |

### Критерії приймання

- **AC-1–5:** API автентифікації, заявок, рейсів і квитків реалізовані в
  належних модулях. Для переходу на PostgreSQL перевірялися HTTP-сценарії,
  зокрема реєстрація та унікальність телефону, розгляд заявки перевізника,
  операції з квитками та збереження сесії після перезапуску.
- **AC-6–7:** блокування рейсу, перевірка місткості й унікальність активного
  квитка реалізовані транзакційно. Ручні перевірки конкурентної купівлі
  останнього місця, одночасних повторів із тим самим ключем та конфлікту при
  іншому payload пройшли.
- **AC-8:** ALS, структуроване логування й response header реалізовані.
  Спеціальний сценарій перевірки кореляції кожного рівня логів у межах
  фінального smoke-набору не виконується.
- **AC-9, AC-11:** перевірялися відмова startup за недоступної БД після трьох
  спроб, runtime readiness/відповідь `503`, відновлення БД та штатний shutdown.
- **AC-10:** зовнішній API збережений після заміни persistence; запити списків
  переглянуті на N+1. Повного автоматизованого порівняння контрактів двох
  сховищ поточний scope не передбачає.
- **AC-12:** класифікація та ліміти retry відповідають специфікації за
  реалізацією. Startup-відмову перевірено вручну; примусове відтворення
  `40001`/`40P01` не входило до мінімального автоматизованого набору.
- **AC-13:** цей аудит містить N+1-перевірку, поведінку при збоях і три
  задокументовані крайові випадки.
- **AC-14–15:** Makefile містить потрібні цілі; `make dev` перевірено з
  PostgreSQL та watch-перезапуском. Smoke перевіряє `/version` і SHA збірки.

Отже, структура загалом відповідає Spec 02 за перевіреним обсягом.
Зазначені вище межі перевірок є обмеженням узгодженого обсягу тестування, а не
твердженням, що всі AC мають окремий автоматизований тест.

## Межі модулів і транзакції

Repositories інкапсулюють SQL, services координують бізнес-сценарії, а
controllers приймають HTTP-запити. Спільний `DatabaseService` надає pool і
транзакційний executor через DI; окремий PostgreSQL idempotency store зберігає
результат повторного запиту в тій самій транзакції, що й бізнес-зміни.

Купівля та скасування блокують рядок рейсу через `FOR UPDATE`, змінюють квиток
і лічильник зайнятих місць атомарно. Унікальні обмеження БД додатково
захищають телефон, активну заявку й активний квиток. Розгляд заявки також
виконує зміну статусу заявки та ролі користувача в одній транзакції.

## Перевірка N+1

N+1 у перевірених списках і деталях не виявлено. Два запити для підрахунку та
отримання сторінки — це фіксована кількість запитів на endpoint, а не запит
для кожного рядка.

| Дані | Фактичний шаблон доступу | Результат |
|---|---|---|
| Список і деталі квитків | Квиток та рейс вибираються одним `JOIN`; для списку окремо виконується `count(*)` | Немає окремого запиту рейсу на кожний квиток |
| Пошук і список рейсів перевізника | SQL-фільтр, сортування та `LIMIT/OFFSET`; окремий підрахунок у тому самому snapshot | Немає додаткових запитів на кожний рейс |
| Списки заявок | Сторінка і підрахунок читають поля заявки без повторних звернень до користувача; ПІБ і телефон збережені у заявці | Немає додаткового запиту на кожну заявку |

Фільтри видимості рейсів та власності заявок/квитків передаються в запити
репозиторіїв до сортування й пагінації.

## PostgreSQL, retries і збої

- Під час startup створюється pool, виконується `SELECT now()`, а міграції
  застосовуються до запуску HTTP listener під PostgreSQL advisory lock.
  Shutdown закриває pool.
- Недоступність PostgreSQL під час startup не дозволяє застосунку почати
  обслуговування HTTP-запитів; перед відмовою виконується не більше трьох
  спроб. Це перевірялося вручну.
- Після startup помилки доступності БД класифікуються як `503`; інші помилки
  репозиторіїв не зводяться автоматично до `503`. SQL і деталі підключення не
  повертаються клієнту.
- У транзакціях повторюються лише serialization failure `40001` і deadlock
  `40P01`, максимум три повтори з backoff `25/50/100 ms` та jitter. Інші
  помилки й невідомий результат `COMMIT` автоматично не повторюються.
  Повтор клієнтом покупки з тим самим `Idempotency-Key` повертає збережений
  результат.
- Зупинка БД після запуску, `503` readiness та відновлення доступності
  перевірялися вручну. Smoke-тест забезпечує лише базову перевірку запуску й
  endpoints, як і передбачено обмеженням лабораторної.

## Три крайові випадки та їх вирішення

1. **Накопичення прострочених idempotency records.** Раніше очищення
   відбувалося тільки при повторному використанні ключа. Тепер після запуску
   та кожні 60 секунд видаляється не більше 1000 прострочених записів зі
   статусом `COMPLETED`; непрострочені та незавершені записи зберігаються.
   `FOR UPDATE SKIP LOCKED` пропускає зайняті рядки; повтор існуючого ключа
   блокує свій рядок до завершення транзакції, щоб очищення не перервало
   replay. Помилки очищення логуються, а shutdown зупиняє таймер і очікує
   завершення поточної операції. Вручну на тестовій БД перевірено межу партії,
   заблокований, непрострочений і незавершений записи, наступну партію,
   автоматичний запуск, очікування поточного очищення при shutdown і
   конкурентний replay під час очищення.
2. **Неузгодженість підрахунку й сторінки.** Обидва запити для всіх п'яти
   списків тепер послідовно виконуються одним client у read-only транзакції
   `REPEATABLE READ`. PostgreSQL `now()` також однаковий у межах транзакції.
   Вручну перевірено конкурентне додавання між підрахунком і сторінкою для
   пошуку рейсів, рейсів перевізника, власних та адміністративних заявок і
   власних квитків; перевірено також сторінку за межами результату. Snapshot
   спільний у межах одного запиту, але не між різними сторінками/HTTP-запитами.
3. **Залежність шляху до міграцій від `process.cwd()`.** Каталог визначається
   від `import.meta.url` у модулі БД. У тимчасових окремих схемах тестової БД
   перевірено фактичне застосування міграції з іншої робочої директорії як
   для скомпільованого коду, так і для безпосередньо створеного source
   `DatabaseService`. Каталог `database/migrations` має зберігатися поруч із
   `dist` або `src`; упаковане production-розгортання залишається поза scope.

## Виправлення dev-запуску

Раніше `make dev` використовував `tsx`, який не генерує decorator metadata
для constructor injection NestJS; HTTP listener не запускався. Dev-запуск
переведено на SWC ESM loader, що використовує налаштування decorator metadata
з `tsconfig.json`; Node watch перезапускає процес після змін джерела.

Перевірено реальний запуск `make dev`, health/readiness, version, список
рейсів, DTO validation (`400` для невалідної реєстрації), зміну відповіді
після зміни source та її відновлення після повернення файлу. Без доступу до
БД dev-entrypoint явно завершується з помилкою після трьох спроб. Додано
мінімальний smoke-тест dev-entrypoint із перевіркою запуску та валідації;
watch перевірено вручну. SWC не виконує typecheck — для цього залишається
окрема команда.

## Перевірки та Definition of Done

Початкові перевірки реалізації PostgreSQL:

- `make db-up` — PostgreSQL Compose сервіс запущено.
- `make db-migrate` — build і застосування/перевірка міграцій завершилися
  успішно.
- `make verify` — успішно пройшли форматування, ESLint, typecheck,
  production build і мінімальний PostgreSQL smoke-тест.
- `git diff --check` — помилок whitespace у diff не знайдено.

Після виправлень повторно пройшли `make verify`, `make db-migrate`,
`npm ls --depth=0`, перевірка форматування змінених документів і
`git diff --check`. Додаткові цільові перевірки наведені в розділі про
крайові випадки. Повноцінні автоматизовані integration/unit/e2e-тести
залишаються поза scope; цільові сценарії проведено вручну на окремій тестовій
БД. Після виправлення `make dev` та smoke-перевірку dev-entrypoint виконано
успішно; `npm audit` не виявив вразливостей.

Самоперевірка за релевантними пунктами `standards/definition-of-done.md`:

- Контекст, мета й scope взяті зі Spec 02; поза scope повні автоматизовані
  тести й production deployment.
- Три крайові випадки та проблему dev-запуску виправлено і перевірено, як
  описано вище.
- Перевірки пройшли; тестовий обсяг навмисно обмежений smoke-тестами й
  попередніми ручними сценаріями відповідно до узгодженого завдання.
- Оновлено пов'язаний verification checklist; аудит, spec та ER-діаграма
  зберігаються в окремих документах.
- Незакомічені зміни PostgreSQL і виправлень залишаються в робочому дереві;
  коміт не створювався.
- Повні unit/integration/e2e-тести залишаються поза узгодженим scope;
  перевірку dev-запуску додано до мінімального smoke-набору.
