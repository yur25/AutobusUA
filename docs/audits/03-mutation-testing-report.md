## Класифікація мутантів, що вижили

`Прийнятний` означає, що мутант може змінювати спостережувану поведінку, але
не порушує явно визначений контракт: це може бути зміна повідомлення чи
логування або поведінка у випадку, який контракт не врегульовує. Такий мутант
не обов'язково є поведінково еквівалентним; наприклад, #142 і #214 змінюють
результат повторного використання ключа для іншого ресурсу, але цей випадок
не визначений контрактом.
`Еквівалентний` означає, що мутант не змінює спостережувану поведінку для
відповідних сценаріїв. ID відповідають фінальному
`reports/mutation/mutation.json`.

### BookingsService

| Mutant (рядок) | Заміна | Класифікація та пояснення |
|---|---|---|
| #142 (31) | Прибирається `tripId` з operation name купівлі, але лишається в request payload | **Прийнятний, але не еквівалентний.** `operation` входить до унікального ключа `(user_id, operation, key_hash)`. Для того самого користувача й ключа повтор на іншому рейсі в оригіналі створює окремий запис, а мутант знаходить попередній запис і повертає `409` через інший request hash. Це не спричиняє replay квитка іншого рейсу. Контракт вимагає `409` для іншого payload, але не визначає, чи повторне використання ключа на іншому рейсі є тією самою операцією; така відмінність не доводить порушення контракту. |
| #143 (33) | Прибирається `tripId` з request payload купівлі, але лишається в operation name | **Еквівалентний.** Operation name лишається прив'язаним до рейсу, а `purchase` не має інших параметрів запиту. Для однакового operation name рейс той самий, тож хеш порожнього payload не змінює replay, конфлікти чи виконання дії. |
| #150 (37), #157 (40), #164 (43), #169 (46), #189 (81), #200 (84), #207 (92), #213 (95), #222 (110), #228 (114), #234 (117), #241 (120), #248 (123) | Текст помилки стає порожнім | **Прийнятний.** Перевірки відмови й відповідні статуси лишаються; змінюється лише текст. |
| #179 (64), #180 (64), #257 (133), #258 (133) | Ім'я події або контекст логування квитка прибирається | **Прийнятний.** Змінюється тільки діагностичне логування. |
| #214 (101) | Прибирається ID квитка з operation name скасування, але лишається в request payload | **Прийнятний, але не еквівалентний.** Через унікальність `(user_id, operation, key_hash)` повтор із тим самим ключем для іншого квитка в оригіналі є окремою операцією, а мутант повертає `409` через request-hash mismatch. Інший квиток не буде помилково відтворений. Контракт не визначає, чи ключ можна повторно використати для скасування іншого квитка, тому ця зміна не доводить порушення вимог. |
| #215 (103) | Прибирається ID квитка з request payload скасування, але лишається в operation name | **Еквівалентний.** Operation name лишається прив'язаним до квитка, а `cancel` не має інших параметрів запиту. Однаковий operation name означає той самий квиток; хеш порожнього payload не змінює replay, конфлікти чи виконання дії. |

Для #142 і #214 висновок стосується лише явно описаного контракту: він не
визначає область унікальності ключа між різними рейсами або квитками. Отже,
ці мутанти не є еквівалентними за поведінкою, але їхній вплив на повторне
використання ключа для іншого ресурсу лишається поза визначеними вимогами.
Тести перевіряють зміну payload у межах одного operation, але не повторне
використання ключа для іншого ресурсу.

## Висновок

Підтверджених непокритих бізнес-прогалин серед цих survivors не залишилося.
Більшість стосується текстів повідомлень і логування; решта є еквівалентними
за поточними умовами або захищена іншою частиною idempotency payload/scope.
Окремо зафіксовано хибний survivor #385 та перевірку, яка доводить, що
відповідний тест виявляє зміну поведінки. Фінальний аудит «топ-3» цим звітом
не виконувався.
