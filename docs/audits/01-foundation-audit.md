# Аудит AutobusUA Foundation

## Мета та межі

Аудит перевіряє:

- відповідність фактичної структури репозиторію `docs/specs/01-foundation.md`;
- наявність і узгодженість каркаса, документації, quality tooling, smoke-тесту
  та git hooks;
- top-level dependencies і підтверджені зайві або неправильні залежності.

Аудит проведено за станом робочого дерева на момент перевірки. Під час аудиту
файли застосунку, конфігурація, залежності та документація, крім цього звіту
і журналу взаємодії, не виправлялися.

Перевірені джерела та команди:

- `docs/specs/01-foundation.md`;
- `README.md`, `standards/`, `docs/adr/`, `docs/er-diagram.md`;
- `src/`, `tests/`, `.husky/`, `package.json`, `package-lock.json`;
- `npm ls --depth=0`;
- пошук використань пакетів у конфігурації, source і тестах;
- `npm audit --omit=optional`;
- `git diff --check`.

## Відповідність структурі специфікації

| Вимога специфікації | Фактичний стан | Результат |
| --- | --- | --- |

| ESM TypeScript/NestJS-каркас у `src/` | Є `src/main.ts`, `AppModule`, health controller і модулі `Auth`, `Carriers`, `Trips`, `Bookings`; `package.json` має `"type": "module"`, TypeScript використовує `NodeNext` | Відповідає |

### Загальний висновок щодо структури

Каркас, документація, стандарти, ESM-конфігурація, smoke-тест і hooks
відповідають описаному foundation scope. Реалізація бізнес-логіки, API,
міграцій і PostgreSQL відсутня, що відповідає out-of-scope для цього етапу.

Критерій AC-6 оновлено відповідно до завдання: аудит має надати топ-3
підтверджені зайві або неправильні залежності. Перевірені матеріали
підтверджують два висновки; третю зайву або неправильну залежність без
доказів вигадувати не потрібно.

## Підтверджені проблеми залежностей

### 1. Поточне відхилення: `@nestjs/testing` не використовується в foundation

**Докази:**

- пакет присутній у `devDependencies` у `package.json`;
- `npm ls --depth=0` підтверджує його встановлення;
- пошук використань у source, tests і конфігурації не знайшов імпортів або
  викликів `@nestjs/testing`;
- специфікація прямо виключає повну реалізацію функціональних та інтеграційних
  тестів на цьому етапі.

**Рішення:** пакет офіційно підтримується NestJS і забезпечує інструменти для
майбутнього тестування застосунку. Він залишаємо в поточному foundation
stack навіть без поточного імпорту.

Якщо під час написання тестів буде доведено, що пакет не потрібен, його можна
безпечно прибрати окремим оновленням залежностей. Для цього не потрібен ADR,
оскільки це інструментальна, а не архітектурна зміна.

### 2. Поточне дерево залежностей має high-вразливість через `picomatch`

**Докази:**

- `npm audit --omit=optional` повідомляє 10 high severity findings;
- у звіті вказана ReDoS-вразливість `picomatch`;
- шлях залежностей проходить через `lint-staged`/`fdir`/`tinyglobby`, а також
  через актуальну гілку `typescript-eslint`;
- npm пропонує `npm audit fix --force`, що передбачає breaking downgrade до
  `lint-staged@16.3.4`.

**Чому це проблема:** встановлений dependency graph має відомий high-ризик.
Це не доводить, що `lint-staged` або `typescript-eslint` зайві: обидва
потрібні для заявлених pre-commit та ESLint-вимог. Проблема саме у виборі
поточних сумісних версій і транзитивному графі.

**Рішення:** наразі не змінювати залежності і не застосовувати
`npm audit fix --force`. Патчованої версії `picomatch` для усунення advisory
ще немає, а запропонований force-fix може вимагає зниження
`lint-staged` і `typescript-eslint` із ризиком порушити конфігурацію.

Безпечна подальша дія — повторно перевірити advisory після випуску сумісних
оновлених версій upstream-пакетів, а потім оновити direct-залежності окремо.
Переходити на тимчасовий `overrides` або до патча в старому графі не потрібно.
Перед прийняттям такого оновлення мають пройти `npm ci`, повний
`npm run verify`, перевірка hooks і повторний `npm audit`.
Для цього рішення ADR не створюється.

## Зафіксовані рішення після діагностики

- `@nestjs/testing` залишаємо до появи реальної потреби прибрати його під час
  тестування.
- Залежності не змінюємо до появи безпечного патчованого оновлення upstream.
- `npm audit fix --force`, downgrades і тимчасові overrides не застосовуємо.
- Код, package manifests, lockfile, ESLint, Prettier і git hooks не змінюються.
- ADR для цих двох рішень не створюється.

## Кандидати, які не визнано findings

`class-validator` і `class-transformer` не імпортуються в поточному source, але
вони є peer-опційними пакетами Nest і безпосередньо пов'язані з уже підключеним
`ValidationPipe` та майбутніми DTO. Поточна відсутність DTO не є достатньою
підставою назвати їх неправильними, тому вони не включені до top findings.

`tsx`, `typescript-eslint`, `eslint-config-prettier`, `husky`, `lint-staged`,
`@types/node`, `reflect-metadata` і `rxjs` мають підтверджене використання у
scripts, конфігурації, source або hooks і не визначені як зайві.

## Підсумок

- Структура репозиторію загалом відповідає foundation spec.
- Підтверджено одну поточну dev dependency-вразливість у транзитивному
  dependency graph через `picomatch`.
- `@nestjs/testing` не вважається зайвим і залишений як офіційний інструмент
  майбутнього тестування.
- Третю проблему не знайдено; припущення для штучного збільшення кількості не
  використовуються.
- Жодне запропоноване рішення під час аудиту не застосовувалося.
