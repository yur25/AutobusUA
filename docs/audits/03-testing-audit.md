## Відповідність структурі специфікації

| Вимога | Фактичний стан | Оцінка |
|---|---|---|
| Unit-тести поруч із класами | 7 файлів `*.spec.ts` розташовані поруч із кодом у `src/common/` та `src/modules/`; `CarriersService` створюється напряму з рукописними фейками | Відповідає |
| Integration-тести з реальною БД | `tests/integration/critical-path.integration.test.ts` підключається до PostgreSQL і відмовляється працювати не з `autobusua_test` | Відповідає |

| Єдина команда тестування | `make test` піднімає Compose PostgreSQL, застосовує тестові міграції, потім запускає unit, integration та E2E; команди видалення БД у цілі немає | Відповідає |
| Окреме мутаційне тестування | Stryker налаштований лише на чотири критичні сервіси та пов'язані unit-тести; survivors мають класифікації у звіті | Відповідає |

## Топ-3 слабких місць тестів

Попередній висновок про відсутність підтверджених прогалин був помилковим.
Рев'юер повідомив про два експерименти з регресіями, які не зламали 98 тестів.
Перший пункт нижче вже підсилено й перевірено окремими регресіями; другий
експеримент рев'юера не повторювався.

1. **Фільтр статусу квитків.** У
   [listTickets](../../src/modules/bookings/bookings.repository.ts) статус
   застосовується окремо до підрахунку та вибірки. Інтеграційний тест
   [скасування](../../tests/integration/critical-path.integration.test.ts)
   запитує `ACTIVE` до скасування єдиного квитка, а `CANCELLED` — після нього:
   у жоден момент у користувача немає одночасно квитків обох статусів. E2E
   [життєвого циклу](../../tests/e2e/carrier-booking.e2e.test.ts) раніше так
   само перевіряв лише наявність потрібного ID через `arrayContaining`. Тому
   відсутність SQL-фільтра може повертати зайві квитки, не порушивши цих
   assertions. Це була прогалина тестів, а не твердження, що поточний SQL
   несправний.
   **Підсилено:** integration створює активний і скасований квитки одного
   користувача, перевіряє точні ID й статуси, count і дві сторінки для кожного
   фільтра, а також список без фільтра. E2E після скасування купує новий
   квиток і для обох статусів перевіряє точний список і metadata. Окреме
   вимкнення фільтра статусу у вибірці та в count змусило обидва тести впасти
   на відповідних assertions; правильний SQL відновлено.

2. **Ізоляція заявок власника.** У
   [findApplicationsByApplicant](../../src/modules/carriers/carriers.repository.ts)
   `applicant_id` обмежує і count, і items; результат містить ім'я та телефон.
   Немає integration-тесту цього методу або E2E запиту
   `/api/v1/carrier-applications/me` із двома заявниками. Unit-тест
   [CarriersService](../../src/modules/carriers/carriers.service.spec.ts)
   перевіряє лише передачу ID, а його фейк записує `userId`, але не фільтрує
   результати. Це залишає потенційне розкриття чужих заявок непоміченим.
   **Майбутнє підсилення:** створити заявки двох користувачів і перевірити для
   кожного власний ID, відсутність чужого, `totalItems` і pagination як через
   PostgreSQL repository, так і через HTTP; виправити фейк, щоб фільтрував за
   `applicantId`. Перевірити окремо регресії count та items.

3. **Ізоляція квитків власника.** Це окрема прогалина в іншому SQL-предикаті
   [listTickets](../../src/modules/bookings/bookings.repository.ts): unit
   перевіряє передачу ID до репозиторію, integration використовує список лише
   для одного власника квитка, а E2E — для одного користувача. Наявний unit
   тест заборони читання чужого квитка за ID не перевіряє список.
   Отже, відсутність обмеження `passenger_id` у count або items не має
   перевірки на конкурентні записи різних власників і може розкрити чужі
   квитки або їх кількість. Цей третій сценарій визначено статичним аналізом;
   окремий експеримент із мутантом не виконувався.
   **Майбутнє підсилення:** створити квитки щонайменше двох користувачів з
   однаковим статусом, перевірити власний ID і відсутність чужого для обох
   користувачів, count і pagination у repository та через HTTP. Забезпечити
   перевірку обох SQL-предикатів, а не лише відповіді `items`.

### Кандидати #142 і #214

Мутанти #142 і #214 змінюють повторне використання одного ключа для іншого
рейсу або квитка: оригінал використовує окрему operation, мутант — спільну й
отримує конфлікт через змінений request hash. Вони не еквівалентні, але
контракт не визначає область ключа між ресурсами. Тому це кандидат на окремий
контрактний тест після рішення про бажану поведінку, а не підтверджений
реальний дефект чи третій пункт топ-3. Деталі — у
[звіті мутаційного тестування](./03-mutation-testing-report.md).

### Чесність фейків та інші списки

- `FakeCarriersRepository.findApplicationsByApplicant` не фільтрує власника;
  `makePage` не застосовує `LIMIT/OFFSET` і порядок, а `createApplication` та
  `reviewApplication` записують виклики, але не відтворюють повний стан
  реального репозиторію. Їхні наявні unit-перевірки делегування не доводять
  коректності repository. Під час підсилення слід реалізувати фільтр власника
  та узгоджене сторінкування для сценаріїв, що від нього залежать; інші
  відмінності враховувати, не видаючи цей фейк за реальну БД.
- `createInlineIdempotencyStore` завжди виконує дію й повертає `replayed:
  false`; stubs репозиторіїв квитків і рейсів повертають заготовлені дані,
  не реалізуючи зберігання, фільтри чи транзакції. Це придатно для ізольованих
  перевірок делегування та гілок сервісу, але не для висновків про replay,
  SQL-фільтрацію чи rollback. Ці властивості потребують окремих integration
  тестів із PostgreSQL.
- Інтеграційний тест видимості рейсів уже порівнює точні ID для двох
  перевізників, зокрема перевіряє відсутність чужого рейсу. Натомість E2E
  пошуку використовує лише `arrayContaining`; при майбутньому підсиленні
  варто створити контрольний невідповідний рейс і перевірити його відсутність,
  не припускаючи, що спільна тестова БД порожня. Для адмінського списку заявок
  наразі також немає integration/E2E перевірки виключення іншого статусу;
  її доцільно розглянути окремо від власницького `/me`.

## Перевірки та висновок

- Історичний `make coverage` — 11/11 unit-тестів, branch coverage `CarriersService`
  100% (10/10).
- Історичний `make mutation` — 403 mutants; 349 killed, 54 survivors. Кожен survivor ID
  присутній серед класифікацій у [звіті мутаційного тестування](./03-mutation-testing-report.md).
- Історичний `make verify` — успішно пройшли format check, lint, typecheck, build,
  81 unit, 14 integration та 3 E2E тести.
- 2026-11-26 `npm run test:unit` — 81/81 unit-тест пройшов без змін коду.
  Під час початкового повторного аналізу Docker daemon не відповідав, тому
  початкові 98 зелених тестів і два експерименти з регресіями були наведені
  зі звіту рев'юера.
- 2026-11-26 після запуску Docker: окремі тимчасові зміни SQL-предикатів
  статусу для items і count призвели до очікуваного падіння як нового
  integration-тесту, так і E2E-тесту. У кожному випадку інший предикат
  залишався правильним; SQL і зібраний застосунок згодом відновлено.
- `make verify` після відновлення SQL пройшов: format, lint, typecheck,
  build, 81 unit, 15 integration і 3 E2E тести. Перша спроба завершилася
  таймаутом наявного dev smoke-тесту; окремий повтор smoke і повторний
  `make verify` пройшли без зміни цього тесту.

Два пункти ізоляції та фейк заявок залишаються непосиленими. Production-код
після експериментів не змінений. Попередні твердження Spec 03 про відсутність
прогалин потребують оновлення на етапі виправлень.
