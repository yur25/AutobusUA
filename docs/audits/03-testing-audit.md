## Топ-3 слабких місць тестів

Попередній висновок про відсутність підтверджених прогалин був помилковим.
Рев'юер повідомив про два експерименти з регресіями, які не зламали 98 тестів.
Усі три пункти нижче підсилено й перевірено окремими регресіями.

1. **Фільтр статусу квитків.** У
   [listTickets](../../src/modules/bookings/bookings.repository.ts) статус
   застосовується окремо до підрахунку та вибірки. Інтеграційний тест
   [скасування](../../tests/integration/critical-path.integration.test.ts)
   запитує `ACTIVE` до скасування єдиного квитка, а `CANCELLED` — після нього:
   у жоден момент у користувача немає одночасно квитків обох статусів. E2E
   [життєвого циклу](../../tests/e2e/carrier-booking.e2e.test.ts) раніше так
   само перевіряв лише наявність потрібного ID через `arrayContaining`. Тому
   відсутність SQL-фільтра може повертати зайві квитки, не порушивши цих
   assertions. Це була прогалина тестів, а не твердження, що поточний SQL
   несправний.
   **Підсилено:** integration створює активний і скасований квитки одного
   користувача, перевіряє точні ID й статуси, count і дві сторінки для кожного
   фільтра, а також список без фільтра. E2E після скасування купує новий
   квиток і для обох статусів перевіряє точний список і metadata. Окреме
   вимкнення фільтра статусу у вибірці та в count змусило обидва тести впасти
   на відповідних assertions; правильний SQL відновлено.

2. **Ізоляція заявок власника.** У
   [findApplicationsByApplicant](../../src/modules/carriers/carriers.repository.ts)
   `applicant_id` обмежує і count, і items; результат містить ім'я та телефон.
   Раніше не було integration-тесту цього методу або E2E запиту
   `/api/v1/carrier-applications/me` із двома заявниками. Unit-тест перевіряв
   лише передачу ID, а фейк записував `userId`, але не фільтрував результати.
   Це залишало потенційне розкриття чужих заявок непоміченим.
   **Підсилено:** integration перевіряє власні та чужі заявки двох заявників,
   count, кілька сторінок і порожній список; E2E перевіряє точний склад списку,
   count та порожню наступну сторінку для обох заявників. Фейк
   [CarriersService](../../src/modules/carriers/carriers.service.spec.ts)
   фільтрує за `applicantId`, сортує та застосовує pagination; unit-тест
   перевіряє результати двох власників і порожнього списку. Тимчасове
   вимкнення фільтра власника окремо для items і count призвело до падіння
   integration та E2E на відповідних assertions; правильний SQL відновлено.
   Тимчасове вимкнення фільтра у фейку призвело до падіння unit-тесту.

3. **Ізоляція квитків власника.** Це окрема прогалина в іншому SQL-предикаті
   [listTickets](../../src/modules/bookings/bookings.repository.ts): unit
   перевіряє передачу ID до репозиторію, а integration і E2E раніше перевіряли
   список лише одного власника квитка. Unit-тест заборони читання чужого
   квитка за ID не перевіряє список. Тому відсутність обмеження `passenger_id`
   у count або items могла розкрити чужі квитки або їх кількість.
   **Підсилено:** integration перевіряє активні квитки двох власників,
   користувача без квитків, точні ID й власників, count та pagination із
   фільтром статусу й без нього. E2E перевіряє порожній список нового
   користувача, а потім точний активний квиток і pagination для обох
   користувачів. Окреме вимкнення фільтра власника для items і count
   призвело до падіння обох тестів на відповідних assertions; правильний SQL
   відновлено.

### Кандидати #142 і #214

Мутанти #142 і #214 змінюють повторне використання одного ключа для іншого
рейсу або квитка: оригінал використовує окрему operation, мутант — спільну й
отримує конфлікт через змінений request hash. Вони не еквівалентні, але
контракт не визначає область ключа між ресурсами. Тому це кандидат на окремий
контрактний тест після рішення про бажану поведінку, а не підтверджений
реальний дефект чи третій пункт топ-3. Деталі — у
[звіті мутаційного тестування](./03-mutation-testing-report.md).

### Чесність фейків та інші списки

- `FakeCarriersRepository.findApplicationsByApplicant` тепер фільтрує
  власника до сортування і pagination. `createApplication` та
  `reviewApplication` записують виклики, але не відтворюють повний стан
  реального репозиторію. Unit-тести з фейком не доводять коректності SQL:
  для цього є окремі integration та E2E перевірки.
- `createInlineIdempotencyStore` завжди виконує дію й повертає `replayed:
  false`; stubs репозиторіїв квитків і рейсів повертають заготовлені дані,
  не реалізуючи зберігання, фільтри чи транзакції. Це придатно для ізольованих
  перевірок делегування та гілок сервісу, але не для висновків про replay,
  SQL-фільтрацію чи rollback. Ці властивості потребують окремих integration
  тестів із PostgreSQL.
- Інтеграційний тест видимості рейсів уже порівнює точні ID для двох
  перевізників, зокрема перевіряє відсутність чужого рейсу. Раніше E2E пошуку
  використовував лише `arrayContaining`, а адмінський список заявок не мав
  перевірки виключення іншого статусу. Ці сценарії підсилено нижче.

## Додаткові перевірки SQL-фільтрів і доступу

Після топ-3 проаналізовано чотири SQL-репозиторії та PostgreSQL-сховище
idempotency. Додано окремі [integration-тести](../../tests/integration/critical-path.integration.test.ts)
та розширено [HTTP-сценарії](../../tests/e2e/carrier-booking.e2e.test.ts):

- Рейси: доступні, заповнені, відправлені й чужі рейси; `AVAILABLE`, `CARRIER`,
  `ALL` та `listMine`, точні ID, кількість і сторінки. Пошук перевіряє обидві
  частини маршруту, регістр, пробіли й включні межі часу з невідповідними
  записами. HTTP окремо перевіряє пошук і деталі заповненого та відправленого
  рейсів для публічного доступу й привілейованих користувачів.
- Адмінські заявки: одночасні `PENDING` і `REJECTED`, відсутність іншого
  статусу, кількість і всі сторінки; HTTP також перевіряє `401` без сесії
  та `403` для заявника. Очікувані результати враховують інші записи БД.
- Авторизація: двоє користувачів і дві сесії, невідомі телефон, ID та hash;
  видалення однієї сесії не видаляє іншу. Це також перевірено через logout
  і `/auth/me`. Строк дії сесії перевіряється guard-ом, а не цими SQL-тестами.
- Активні квитки: два пасажири на одному рейсі, той самий пасажир на іншому
  рейсі та виключення скасованого квитка. HTTP перевіряє відмову в перегляді
  й скасуванні чужого квитка та збереження його активного стану.
- Idempotency: однаковий ключ і payload для різних користувачів, а також
  окремі operation і ключ для одного користувача; replay повертає відповідний
  результат. Окремо перевірено, що обробка ключа іншого користувача не видаляє
  чужий прострочений запис. Це не вирішує відкладене питання про область
  ключа між різними цільовими ресурсами.

На правильній реалізації тести пройшли. Додатково виконано **24 окремі
integration та 6 HTTP негативних експериментів**: тестовий перехоплювач
тимчасово підміняв SQL на рівні драйвера PostgreSQL, не змінюючи
production-файли. Кожен експеримент підтвердив застосування підміни й падіння
відповідного тесту через неправильний результат або бізнес-конфлікт, а не
через невалідний SQL:

| Предикати, ослаблені окремо | Integration | HTTP |
|---|---:|---:|
| Час відправлення, місткість, власник у пошуку рейсів | 3 | 2: час і місткість |
| Власник `listMine`: count та items | 2 | — |
| Origin, destination, нижня й верхня межі часу; окремо заміна кожної включної межі на виключну | 6 | 1: origin |
| Статус адмінських заявок: count та items | 2 | 2 |
| Пошук за телефоном, ID, hash сесії; видалення сесії | 4 | 1: видалення сесії |
| Активний квиток: пасажир, рейс і статус | 3 | — |
| Idempotency replay: користувач, operation, key; видалення простроченого ключа: власник | 4 | — |

Експерименти з видаленням навмисно обмежувалися створеними тестом сесіями або
записами; глобальне очищення не мутувалося. У пошуку рейсів `items` і `count`
використовують спільний `buildWhere`, тоді як окремі запити `listMine` і
адмінських заявок перевірялися окремими підмінами.

### Ізоляція фонового очищення idempotency (AC-4)

Планувальник у [PostgresIdempotencyStore](../../src/common/postgres-idempotency.store.ts)
за замовчуванням лишається ввімкненим у звичайному застосунку. Явний прапорець
`IDEMPOTENCY_CLEANUP_SCHEDULER_ENABLED=false` вимикає лише його автоматичний
запуск; запити й далі видаляють конкретний власний прострочений ключ під час
`executeIdempotently`.

Прапорець встановлюється в [Vitest setup](../../tests/setup.ts), передається
процесу основного E2E та smoke-застосунків і задається в
`migrate-test.mjs`. Тож scheduler не запускається автоматично у процесах,
що працюють зі спільною `autobusua_test`. Unit-тест перевіряє default-on
поведінку, хвилинний інтервал, зупинку таймера, відсутність планування за
прапорцем і відмову запуску за некоректного значення.

Окремий PostgreSQL integration-тест викликає одноразовий метод із тим самим
SQL-предикатом у явній транзакції. Тест створює тимчасову таблицю за структурою
справжньої, перевіряє, що SQL звернеться саме до неї, та ізольовано перевіряє
видалення простроченого `COMPLETED` і збереження `IN_PROGRESS` та
непростроченого `COMPLETED`. Потім транзакція відкочується. Це не видаляє й не
блокує сторонні записи спільної таблиці; тимчасова таблиця автоматично
прибирається. Ручний запуск планувальника в integration-тесті прибрано.
Окреме тимчасове ослаблення кожного з двох SQL-предикатів — статусу та
терміну дії — спричинило падіння тесту на перевірці результату; з правильним
SQL тест пройшов. Підміни діяли лише в тестовому процесі й над тимчасовою
таблицею.

Ця ізоляція стосується процесів тестового набору. Незалежний застосунок,
підключений до спільної тестової БД із увімкненим планувальником, може й надалі
видаляти прострочені записи.

Stryker не розширювали на репозиторії: поточний runner охоплює unit-тести
сервісів, а заміна цілого SQL-рядка може спричинити синтаксичну помилку без
перевірки конкретного фільтра. Наведені валідні зміни предикатів на реальній
PostgreSQL перевіряють ці ризики адресно. Це не доказ захисту кожного
SQL-предиката: зокрема, переходи заявки `PENDING`, роль `PASSENGER` і
глобальне очищення idempotency не пройшли окремого повного мутаційного аналізу.

  статусу для items і count призвели до очікуваного падіння як нового

  залишався правильним; SQL і зібраний застосунок згодом відновлено.

  build, 81 unit, 15 integration і 3 E2E тести. Перша спроба завершилася
  таймаутом наявного dev smoke-тесту; окремий повтор smoke і повторний
  `make verify` пройшли без зміни цього тесту.
- Після підсилення ізоляції заявок `make verify` пройшов: format, lint,
  typecheck, build, 82 unit, 16 integration та 4 E2E тести. `make coverage`:
  12 unit-тестів, 100% логічних гілок `CarriersService` (10/10).
- Окремі тимчасові зміни SQL-предикатів власника для заявок у items та count
  спричинили очікуване падіння обох нових integration/E2E тестів. Кожен раз
  інший предикат залишався правильним; SQL і зібраний застосунок відновлено.

  власника у вибірці та в count спричинило падіння integration та E2E тестів.
  Після відновлення SQL `make verify` пройшов: format, lint, typecheck,
  build, 82 unit, 17 integration і 4 E2E тести.
- Після додаткового підсилення `make verify` пройшов: format, lint, typecheck,
  build, 82 unit, 24 integration і 4 E2E тести. Stryker повторно не запускався;
  результати ручних негативних експериментів наведено вище.
- Після ізоляції фонового очищення `make verify` пройшов: format, lint,
