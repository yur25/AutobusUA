Ще однією з вимог завдання є налаштування керування залежностям - щоб через усі рівні застосунку не протягувалось багато параметрів. Ще врахуй рекомендації з лабораторної щодо роботи з БД: явна ініціалізація підключення під час запуску застосунку з перевіркою доступності через `SELECT now()`, ізольоване локальне середовище (а не 5432/5433/5434 на localhost), окрема база для тестових прогонів або гілок та одна узгоджена стратегія розміщення моделей.
Під час проєктування запитів до БД зверни увагу на можливі проблеми N+1, особливо під час отримання списків квитків, рейсів і заявок разом із пов'язаними даними. Під час переходу на реальну БД передбач транзакції для операцій, що змінюють пов'язані дані, валідацію вхідних даних і бізнес-обмежень, обробку помилок БД, а також ідемпотентність і безпечну стратегію повторних запитів там, де можливі retries.

## Асистент — початковий аналіз

Перечитано `docs/specs/01-foundation.md`, `docs/er-diagram.md`, стандарти,
README, ADR-и та поточний NestJS-каркас. Foundation визначає модульний моноліт
із модулями `Auth`, `Carriers`, `Trips`, `Bookings`, серверними сесіями,
PostgreSQL, лічильником `occupied_seats` і блокуванням рейсу під час купівлі та
скасування. Реалізація бізнес-логіки, API, репозиторіїв і PostgreSQL ще не
починалася.

Поточний промпт розширює scope лабораторної 2 до робочого HTTP API з
двоступеневою реалізацією: спочатку static storage через ті самі сервісні
контракти, потім PostgreSQL. Потрібно зберегти межі controller → service →
repository, exception layer NestJS, request/business-process context,
транзакції, N+1-контроль, ідемпотентність та аудит.

### Попередні висновки щодо контексту та логування

1. **Native `AsyncLocalStorage` + Nest middleware/interceptor + DI logger.**
   Middleware створює контекст на початку кожного HTTP-запиту, генерує
   `crypto.randomUUID()` як business-process ID, а singleton logger читає його
   з ALS. Це не потребує ручного передавання ID через controller, service і
   repository та відповідає офіційному Nest recipe.
2. **`nestjs-cls` або аналогічний готовий CLS-пакет.** Зменшує власний
   infrastructure-код і може спростити доступ до контексту, але додає
   залежність та ще один абстракційний шар для вимоги, яку можна реалізувати
   стандартною бібліотекою Node.js.
3. **Request-scoped providers.** Дають DI-доступ до контексту, але поширюють
   request scope на залежні providers, ускладнюють життєвий цикл і створюють
   додаткову вартість на кожен запит. Для одного ID та optional user context
   це гірше за ALS.
4. **Ручне передавання context object.** Найбільш явне і типобезпечне, але
   прямо суперечить вимозі не протягувати business-process ID та user context
   через усі рівні.

Попередня рекомендація: native `AsyncLocalStorage` із власним типізованим
request context, Nest middleware для ініціалізації, DI-managed logger для
отримання контексту та interceptor/exception filter для завершальних логів.
Це лише пропозиція для обговорення, не зафіксоване рішення.

### Попередні висновки щодо SQL та ORM

1. **Prisma.** Дає типізований client, schema, міграції, базовий transaction
   API та зручні CRUD-запити. Недоліки для цього завдання: SQL-репозиторії
   приховуються за ORM, точний `SELECT ... FOR UPDATE` і транзакційний client
   потребують raw SQL або окремого обходу, а дві моделі зберігання
   (Prisma schema плюс domain types) можуть розмити домовленість про єдине
   розміщення моделей.
2. **`pg` / node-postgres і звичайний параметризований SQL.** Найкраще
   відповідає вимозі «SQL у репозиторіях», дає прямий контроль над JOIN,
   `SELECT ... FOR UPDATE`, транзакціями, таймаутами та обробкою кодів
   PostgreSQL. Недоліки: типи результатів, mapping, міграції та SQL-дисципліну
   треба підтримувати власним кодом.
3. **Query builder (наприклад, Kysely).** Дає типобезпечні запити і менше
   ручного mapping, але додає abstraction layer; для навчального scope це
   компроміс між Prisma і raw SQL, а не найпростіший варіант.

Попередня рекомендація: `pg` + параметризований SQL + окрема стратегія
міграцій, оскільки вже погоджені PostgreSQL, row-level locking і repository
boundary. Prisma залишається розумним вибором, якщо пріоритетом є
автоматичне генерування типів і зручність CRUD, але тоді треба окремо
зафіксувати межі raw SQL для конкурентних операцій.

### Питання, які треба узгодити до створення spec

1. Підтвердити або відхилити native `AsyncLocalStorage` як механізм request
   context і business-process ID. Якщо підтвердити, окремий ADR опише
   alternatives, межі контексту, формат ID, життєвий цикл і правила логування.
2. Визначити, чи user identity також читається з ALS після auth guard, чи лише
   business-process ID, а user передається до service через типовий auth
   principal/decorator. Це важливо для безпеки та явності authorization.
3. Визначити назву контракту: `businessProcessId`, `requestId` чи обидва
   (наприклад, зовнішній request ID плюс внутрішній business-process ID).
4. Підтвердити SQL stack: `pg` + raw SQL, Prisma, або query builder. Для
   raw SQL потрібно визначити стратегію migration tooling і розміщення
   SQL-моделей/типів.
5. Визначити прототипний static storage: тільки in-memory для одного процесу
   чи також тестова реалізація repository contracts, яка повністю повторює
   PostgreSQL interface.
6. Для PostgreSQL уточнити локальну ізоляцію: Docker Compose без host port
   publish, або configurable non-default host port; і схему окремих database
   для app, tests і branch/run.
7. Визначити політику старту при недоступній БД: fail-fast і завершення
   застосунку чи degraded mode. Для цього API рекомендовано fail-fast із
   явним startup error та health/readiness failure.
8. Визначити мінімальний API contract: endpoint-и, формати DTO/error response,
   cookie/session behavior, pagination/filtering і idempotency key policy.

## Асистент — уточнення пагінації та ідемпотентності

### Пагінація

Так, логічний порядок має бути таким:

1. перевірити автентифікацію та роль;
2. застосувати authorization і бізнес-фільтри;
3. застосувати стабільне сортування;
4. застосувати pagination;
5. повернути результат.

У SQL це логічно відповідає `WHERE` → `ORDER BY` → `LIMIT/OFFSET` (хоча
оптимізатор PostgreSQL може виконувати план в іншому фізичному порядку).
Пагінувати дані до authorization-фільтра не можна: це може дати неправильні
сторінки та потенційно розкрити чужі записи.

Для прикладу:

- пасажир отримує лише рейси з майбутнім часом відправлення та доступною
  місткістю;
- перевізник отримує лише рейси, де `carrier_id` дорівнює його user ID;
- адміністратор отримує окремий адміністративний список із дозволеним
  scope даних.

Фільтрація повинна виконуватися в repository-запиті, а не після завантаження
всіх рядків у service. Це одночасно забезпечує безпеку, правильну пагінацію і
менше навантаження на БД.

Для поточного масштабу пропонується page-based pagination з обмеженням
`pageSize`. Сортування має бути детермінованим, наприклад:
`departure_at ASC, id ASC`, щоб записи з однаковим часом не перескакували між
сторінками. Максимальний `pageSize` треба обмежити.

Cursor pagination краще поводиться при частих вставках і змінах, але складніша
для API та навчальної реалізації. Її можна залишити для наступного етапу,
якщо обсяг даних або вимоги продуктивності це виправдають.

### Класифікація помилок БД

Помилки не слід перетворювати на `503` одним широким catch. На repository
boundary потрібен типізований mapper:

- помилка з'єднання, недоступний сервер, timeout або закритий client —
  `503 Service Unavailable`;
- порушення unique constraint (`23505`) — `409 Conflict`;
- порушення foreign key (`23503`) — `400` або `409` залежно від сценарію;
- порушення check constraint (`23514`) — `400 Bad Request`;
- serialization failure/deadlock (`40001`, `40P01`) — обмежений retry лише для
  безпечної транзакції або явна помилка, а не безкінечний retry;
- відсутній рядок — service повертає `NotFoundException`, а не `503`;
- неочікувана SQL-помилка — `500` із повним внутрішнім логом, але без деталей
  БД у HTTP-відповіді.

Це можна реалізувати через один database error mapper/filter, а не через
`try/catch` у кожній функції.

### Таблиця ідемпотентності

Для `Idempotency-Key` потрібен окремий запис із приблизно такими даними:

- `id`;
- `key`;
- `operation`;
- `user_id`;
- hash нормалізованого request payload;
- стан `IN_PROGRESS` або `COMPLETED`;
- HTTP status і response payload для повторного повернення;
- resource ID, якщо операція створила ресурс;
- `created_at`, `completed_at`, `expires_at`.

Унікальність має бути визначена щонайменше за
`(user_id, operation, key)`.

Правила:

1. Перший запит реєструє ключ і виконує операцію.
2. Повтор із тим самим ключем і тим самим payload повертає збережений
   результат, не створюючи другий ресурс.
3. Повтор із тим самим ключем, але іншим payload отримує `409 Conflict`.
4. Паралельний запит із тим самим ключем бачить `IN_PROGRESS` і отримує
   `409 Conflict` або контрольований retry response, але не запускає операцію
   вдруге.
5. Для купівлі квитка ідемпотентний запис та створення квитка мають бути в
   одній транзакції.
6. Окремий database unique constraint на активний квиток залишається
   незалежним захистом від різних idempotency keys.

Потрібно ще узгодити, для яких операцій `Idempotency-Key` є обов'язковим.
Моя рекомендація: для всіх state-changing POST-операцій, які можуть безпечно
повторитися після network timeout, а мінімально обов'язково — для купівлі
квитка.

## Асистент — пояснення SWC

**SWC** — компілятор, який перетворює TypeScript на JavaScript. У нас він
використовується лише для dev-запуску, а production build, як і раніше,
виконує `tsc`.

### Чому обрав

Попередній `tsx` у dev-запуску не генерував metadata декораторів: NestJS не
міг визначити залежності конструкторів і застосунок не запускався. SWC
підтримує потрібну metadata. Я перевірив запуск із PostgreSQL, валідацію DTO
та перезапуск після зміни коду.

Розглядав і Nest CLI: доступна v12 вимагала новішого Node для частини
залежностей, а v11 додавала вразливі транзитивні залежності. Спроба `ts-node`
зіткнулася з несумісністю ESM-резолвінгу. SWC запрацював у поточному
середовищі; перевірка `npm audit` тоді не виявила вразливостей.

### Поточна конфігурація

Окремого `.swcrc` немає. `@swc-node/register` бере налаштування з
[tsconfig.json](</D:/For code/KPI/Nodejs/AutobusUA/AutobusUA/tsconfig.json>),
зокрема:

```json
{
    "experimentalDecorators": true,
    "emitDecoratorMetadata": true,
    "module": "NodeNext",
    "target": "ES2023",
    "sourceMap": true
}
```

Для запуску використовується команда з
[package.json](</D:/For code/KPI/Nodejs/AutobusUA/AutobusUA/package.json>):

```json
"start:dev": "node scripts/write-build-info.mjs && node --enable-source-maps --import @swc-node/register/esm-register --watch scripts/start-dev.mjs"
```

- `@swc/core` виконує компіляцію, `@swc-node/register` інтегрує її з ESM
  loader Node.js.
- `--watch` перезапускає процес при зміні завантажених файлів;
  `--enable-source-maps` допомагає зіставити помилки з TypeScript.
- [start-dev.mjs](</D:/For code/KPI/Nodejs/AutobusUA/AutobusUA/scripts/start-dev.mjs>)
  завантажує `.env`, якщо він існує, і запускає застосунок.

**Важливе обмеження:** SWC не перевіряє типи. Для цього залишаються
`make typecheck` і `make verify`. `tsx` досі використовується для запуску
smoke-тестів, але не для dev-запуску самого застосунку.
