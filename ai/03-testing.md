### Рекомендація: перейти на Vitest для наступного етапу тестування

Поточний `node:test` працює й має важливі переваги: він входить до Node.js,
не додає окремий test-runner dependency, підтримує async-тести, ізоляцію
тестових процесів і вбудовані mock API. Для простих smoke-тестів, які
піднімають HTTP-процес і перевіряють endpoints, його цілком достатньо.

Однак майбутнє завдання охоплює не лише smoke-тести, а й багато unit- та
integration-сценаріїв із Nest DI, репозиторіями, конкурентністю, імітацією
помилок і часу, а також mutation testing через Stryker. Для цього Vitest
пропонує єдиний набір assertions, spies/mocks, fake timers, фільтрацію тестів,
watch mode та конфігуровані coverage reporters. Для ESM/TypeScript він має
першокласну підтримку; це зменшує потребу самостійно складати runner із
Node.js API, `tsx` та додаткових засобів mocking.

Для Stryker є офіційний Vitest runner plugin. StrykerJS також має TAP runner,
який може запускати Node.js `node:test` (і приймати `--import tsx`), тож
перехід на Vitest не є технічно обов'язковою умовою мутаційного тестування.
Vitest дає більш інтегрований шлях для мутаційного циклу й test selection,
але обмеження його Stryker runner слід врахувати в окремому налаштуванні.

Nest CLI для ESM-шаблонів використовує Vitest за замовчуванням, але це
самостійне Nest-застосування: Vitest не замінює `@nestjs/testing` і не змінює
архітектуру тестів через Nest testing module. Наш репозиторій не створено
Nest CLI і зараз має власний мінімальний `node:test` smoke runner.

**Моя пропозиція:** використовувати Vitest як спільний runner для нових
unit/integration/E2E тестів і Stryker, за потреби мігрувавши поточні smoke
тести в межах погодженого обсягу. Причина — очікуваний набір різних типів
тестів і потреба в зрілих mocks/coverage/mutation integration, а не сам факт,
що це типовий Nest інструмент. `node:test` варто залишати, якщо пріоритетом є
мінімум dev-залежностей і простота smoke-набору; за такого рішення Stryker
можна під'єднати через TAP runner, але mocking і частину test tooling
доведеться організувати окремо.

Джерела: [Nest CLI](https://docs.nestjs.com/cli/usages),
[Vitest features](https://vitest.dev/guide/features),
[Stryker Vitest runner](https://stryker-mutator.io/docs/stryker-js/vitest-runner/),
[Stryker TAP runner](https://stryker-mutator.io/docs/stryker-js/tap-runner/) і
[Node.js test runner](https://nodejs.org/docs/latest-v24.x/api/test.html).

Перед початком підготовки тестів потрібне підтвердження вибору runner.

## Асистент — детальніше про Vitest

### Що вже є

Smoke-тести використовують `node:test` і запускають зібраний застосунок як
окремий процес. Команда `tsx --test` потрібна для виконання самих TypeScript
файлів тестів; це окремо від вибору API тестового runner. Зараз тести
перевіряють health/version/readiness, список рейсів і запуск dev-entrypoint
із базовою DTO-валідацією.

### `node:test` для цього backend

**Переваги**

- Вбудований у Node.js 24: немає окремого runner dependency або конфігурації.
- Є assertions через `node:assert`, ізоляція тестів, async lifecycle hooks,
  spies/mocks для функцій, методів і таймерів.
- Добре пасує smoke/E2E через реальний HTTP listener і окремий процес; для
  інтеграційних тестів із реальною PostgreSQL він також достатній.
- Nest `TestingModule` і `overrideProvider()` працюють незалежно від runner.
  Тобто service-тести часто можуть підміняти репозиторій через DI, не
  перехоплюючи імпорти модулів.
- StrykerJS має TAP runner для тестів, що виводять TAP; офіційна документація
  прямо називає вбудований Node test runner. Для TypeScript можна налаштувати
  `nodeArgs` із loader і окремий build command.

**Недоліки**

- Runner не компілює TypeScript. Потрібен окремий loader або компіляція;
  поточний `tsx` запускає smoke-файли, але сам по собі не генерує Nest
  decorator metadata для імпортованих source-класів.
- Немає вбудованого аналога `vi.mock()` для заміни ESM-модуля до його
  завантаження. Це важливо для unit-тестів, де DI підміна незручна або
  залежність створюється на рівні модуля; тоді знадобиться інший дизайн
  залежності чи додатковий інструмент.
- Stryker інтегрується через TAP протокол і власну конфігурацію запуску/build.
  Це підтримуваний шлях, але не такий спеціалізований, як Stryker Vitest
  runner.

### Vitest для цього backend

**Переваги**

- TypeScript/ESM підтримуються без окремого виклику test-файлів через `tsx`.
- Є `vi.fn`, spies, fake timers, модульні mocks, test filtering, watch mode і
  coverage reporters в одному інструменті. Це зручно для гілок сервісів:
  DB-помилок, expiry/часу, невдалих репозиторних результатів та зовнішніх
  залежностей.
- Є офіційний Stryker Vitest runner, тому можна використовувати інтеграцію
  mutation testing замість адаптації через загальний TAP runner.
- Nest CLI справді додає Vitest у сучасні ESM-заготовки, але це лише типовий
  шаблон CLI, не вимога Nest і не аргумент сам по собі.

**Недоліки та особливості саме в нашій конфігурації**

- Vitest додає залежності й конфігурацію. Його вбудоване виконання TypeScript
  не означає автоматичну підтримку Nest metadata: трансформація декораторів
  має бути налаштована окремо. Потрібно перевірити SWC/Vitest integration
  перед тим, як покладатися на `@nestjs/testing` із source-класами. Або
  тестувати класи через ручне створення екземплярів/DI mocks, або імпортувати
  скомпільовані модулі.
- Workers можуть паралельно запускати тести, а кілька тестів торкатимуться
  спільної PostgreSQL. Для інтеграційних/E2E тестів треба окремо спланувати
  ізоляцію даних/схем або вимкнення паралельності там, де є спільний стан.
- Stryker Vitest runner сам запускає тести в одному thread і має власний
  mutation coverage. Для тестів, які перевіряють застосунок через HTTP
  замість прямого імпорту мутованих модулів, у Stryker треба налаштувати
  вибір тестів так, щоб такі тести не були відкинуті як непов'язані.

### Як це впливає на наші сценарії

- **Unit (services/guards):** обидва варіанти працюють. Nest DI з mock
  providers знімає багато потреб у module mocking; Vitest зручніший для
  timers, spies та гілок, які треба ізолювати.
- **Integration (repositories + тестова PostgreSQL):** обидва можуть запускати
  сценарії. Вирішальні питання — керування транзакціями/даними, ізоляція та
  cleanup; runner сам їх не вирішує.
- **E2E (HTTP + PostgreSQL):** поточний `node:test` уже довів придатність для
  простих HTTP smoke. Vitest не робить E2E автоматично надійнішим; потрібні
  lifecycle керування процесом, тестова БД і cleanup.
- **Stryker:** офіційно підтримуються обидва шляхи: Vitest runner або TAP
  runner для `node:test`. Vitest шлях більш інтегрований, Node шлях легший за
  залежностями, але потребує узгодити TypeScript build/loader.

### Виважена рекомендація

Для повного майбутнього набору Vitest — найзручніший вибір, якщо ми готові
додати runner і налаштувати Nest decorator metadata та серіалізацію доступу до
тестової БД. Причина — це не те, що він «за замовчуванням» у Nest, а єдина
інтегрована підтримка unit mocks, timers, coverage і офіційного Stryker runner.

`node:test` також цілком обґрунтований, якщо пріоритет — мінімальні залежності
та нативне середовище Node. Оскільки більшість наших критичних компонентів
можна підміняти через Nest DI, його нестача module mocking може бути менш
важливою, ніж для frontend-коду. Stryker можна запустити через TAP runner.
Тому це не блокер для тестового завдання і не потрібно переходити лише через
використання Nest.

Моя перевага — Vitest для unit/integration та Stryker; наявний E2E smoke можна
залишити на `node:test`, якщо не буде користі мігрувати його. Але змішування
двох runner додає команд і підтримки, тож краще вирішити, чи важливіша
уніфікація, чи мінімум змін/залежностей. Чекаю на ваше рішення, перш ніж
починати покривати критичні гілки.

## Асистент — детальніше про моки

Мок — це тестова заміна залежності, щоб керувати її результатом і перевірити
взаємодію з нею. На практиці розрізняють:

- **stub** — повертає заздалегідь задані дані або помилку;
- **spy** — зберігає/викликає реальну реалізацію, але дозволяє перевіряти
  виклики;
- **mock** — тестовий double, поведінка та очікування взаємодії якого
  задаються тестом. У розмові «mock» часто вживають як загальну назву для
  всіх таких double.

### Наш типовий випадок: мок через Nest DI

`BookingsService` отримує `BookingsRepository`, `IdempotencyStore` і logger
через constructor injection. Для unit-тесту найпростіше передати fake/mock
repository безпосередньо або надати його в `@nestjs/testing` через
`overrideProvider(BOOKINGS_REPOSITORY)`. Це не потребує перехоплювати ESM
імпорти й однаково працює з `node:test` та Vitest.

Наприклад, для гілок `purchase` можна налаштувати fake repository так, щоб
він повертав рейс із вільним місцем, повний рейс, уже наявний активний квиток
або відхиляв `createTicket`. Тоді перевіряємо результат сервісу й важливі
побічні ефекти: чи не змінювався лічильник при помилці, чи викликалися
створення квитка та збільшення місць. Аналогічно у `cancel` перевіряємо
власника, статус, час відправлення, зменшення лічильника і відсутність
часткових дій при відмові.

Vitest спрощує створення та перебудову spies:

```ts
const findTripForUpdate = vi.fn().mockResolvedValue(futureTrip);
const createTicket = vi.fn().mockResolvedValue(undefined);
```

Для того самого підходу в `node:test`:

```ts
const findTripForUpdate = t.mock.fn(async () => futureTrip);
const createTicket = t.mock.fn(async () => undefined);
```

Точний API конфігурації реалізацій і викликів у цих runner-ів відрізняється,
але для простих repository fakes різниця не принципова. У `node:test` mocks,
створені через test context `t.mock`, автоматично відновлюються після тесту.
У Vitest поведінку між тестами потрібно організовано скидати/відновлювати
через конфігурацію або hooks (`clearMocks`, `mockReset`, `restoreMocks` тощо).
Це зручно, але якщо конфігурацію не задати, стан викликів чи поведінка
mock-ів можуть протікати між тестами.

### Коли потрібен mock цілого ESM-модуля

Це інший рівень, ніж DI provider. Він потрібен, коли код безпосередньо
імпортує функцію/об'єкт і залежність не передається конструктором. Наприклад,
`AuthService` напряму імпортує Argon2 функції та Node crypto helpers. Для
більшості сценаріїв краще мокати repository через DI, а Argon2 залишити
реальним у небагатьох перевірках хешування/логіну. Модульний mock може бути
корисний, якщо тесту треба примусово відтворити конкретну криптографічну
помилку без витрат реального хешування.

Vitest має `vi.mock(...)`: виклики піднімаються до імпортів, тому mock
встановлюється до evaluation залежного модуля:

```ts
vi.mock("argon2", () => ({
    hash: vi.fn().mockResolvedValue("test-hash"),
    verify: vi.fn().mockResolvedValue(true),
}));
```

Це спрощує ESM mocking і дозволяє контролювати виклики `hash`/`verify`, але
має власні правила hoisting, cache і reset-ів. Важливо не перетворювати такі
тести на перевірку самих mocks: якщо ми всюди мокаємо Argon2 і repository,
тест уже не перевіряє persistence чи криптографічну інтеграцію.

У `node:test` на Node.js 24.13.1 модульний mock теж існує: `t.mock.module()`.
Моя попередня фраза, що built-in runner зовсім не має аналога module mocking,
була неточною. Відповідно до документації Node.js v24.13.1, ця можливість має
статус **Early development** і вимагає запуску Node із
`--experimental-test-module-mocks`. Крім того, код під тестом треба
завантажити після налаштування mock-у (зазвичай dynamic `import()`); вже
завантажені імпорти не переписуються. Це гірша ергономіка та стабільність, ніж
`vi.mock`, а не повна відсутність функції.

### Що не варто мокати в наших типах тестів

- **Unit:** зовнішні межі (repository, logger, clock/crypto, за потреби
  Argon2) можна підміняти; бізнес-логіку самого сервісу треба залишати
  реальною.
- **Integration repository + PostgreSQL:** використовуємо справжню тестову
  БД, міграції, SQL і constraints; мок `pg` прибрав би саме те, що цей тест
  повинен перевірити.
- **E2E:** запускаємо реальне Nest-застосування і справжню тестову PostgreSQL;
  підміняти можна лише те, що явно поза межами тестового середовища.
- **Конкурентність, транзакції, ідемпотентність:** потрібні справжні
  паралельні запити/транзакції до тестової БД. Моки корисні для точкових
  помилок, але не доводять поведінку PostgreSQL при гонках.
- **Stryker:** надмірне мокання може приховати регресії. Для mutation testing
  потрібні assertions про observable behavior, а не лише «метод X викликано».

### Висновок саме щодо моків

Для основної частини критичних unit-тестів цього проєкту обидва варіанти
достатні: Nest DI дозволяє передавати fake repositories і idempotency store
без ESM module mocking. Тож самі mocks не є вирішальним аргументом на користь
Vitest.

Практична різниця виникає для складніших spies, fake timers, module mocking і
Stryker integration: у Vitest ці можливості стабільніші й більш
уніфіковані; `node:test` має сильні built-in function/method/timer mocks, але
модульний mock експериментальний у Node 24.13.1. Через це я й далі трохи
схиляюся до Vitest для великого тестового набору, але якщо ми будуватимемо
unit-тести переважно через DI fakes та інтеграційні тести з реальною БД,
залишитися на `node:test` — цілком розумний, простіший варіант.

Джерела: [Node.js v24.13.1 test runner](https://nodejs.org/docs/v24.13.1/api/test.html),
[Vitest mocking](https://vitest.dev/guide/mocking) і
[Stryker Vitest runner](https://stryker-mutator.io/docs/stryker-js/vitest-runner/).
Рішення про runner і написання тестів поки очікуються; код не змінювався.

## Користувач — наскільки важливий недолік `node:test`

Можеш детальніше пояснити за цей найбільший мінус node:test який ти згадував - хочу зрозуміти чи справді варто обирати vitest

## Асистент — оцінка практичної ваги недоліку `node:test`

Уточню попередню рекомендацію: «найбільший мінус» — це не те, що на `node:test`
неможливо робити mocks. У ньому є function/method/timer mocks, а у Node.js
24.13.1 також є module mock API `t.mock.module()`. Вузька різниця полягає в
тому, що module mocking у цій версії має статус **Early development**, вимагає
`--experimental-test-module-mocks` і потребує встановлювати mock до імпорту
модуля. Vitest `vi.mock()` для цього зріліший і зручніший. Це недолік тільки
коли тест справді мусить замінити безпосередньо імпортований ESM-модуль.

У нашому застосунку багато критичних сценаріїв проходять через Nest DI. Для
unit-тесту сервісу можна підмінити repository або idempotency store як
provider/fake і перевірити бізнес-результат та побічні ефекти. Такий тест
працює з будь-яким runner-ом і не потребує module mocking. Помилку БД можна
відтворити fake repository, який повертає rejected promise; правильність SQL,
транзакцій і гонок окремо перевіряти реальною тестовою PostgreSQL.

У коді є й безпосередні імпорти, наприклад Argon2 та crypto/time helpers у
`AuthService`. Тут Vitest може спростити окремі ізольовані сценарії. Але
модульний мок не є автоматично кращим тестом: він може приховати інтеграційні
проблеми. За потреби ці залежності можна перевіряти реально або згодом
передавати через ін'єкцію; рішення про зміну дизайну зараз не приймається.

Надані smoke-тести в `tests/smoke-test.ts` запускають справжній застосунок
окремим процесом, роблять HTTP-запити й використовують тестову БД. У них
модульні моки майже не потрібні; `t.after()` уже забезпечує cleanup процесу.
Перехід на Vitest не зробить ці smoke/E2E-перевірки якіснішими сам по собі —
це буде переважно зміна runner API та конфігурації.

Окремо Stryker: у нього є офіційні інтеграції як для Vitest, так і для TAP
runner, який підтримує `node:test`. Для TAP доведеться явно налаштувати
TypeScript loader/build і runner config; Vitest шлях більш спеціалізований,
але не єдиний. Жоден runner не вирішує ізоляцію спільної тестової БД:
паралельність і cleanup треба планувати окремо.

**Висновок:** попереднє «трохи схиляюся до Vitest» було сильніше, ніж дозволяє
сам аргумент про моки. Для наших DI-based сервісних тестів цей аргумент слабкий.
Vitest варто обрати, якщо разом важливі уніфікований багатший runner, зручні
module mocks і більш прямий Stryker integration; залишитися на `node:test`
варто, якщо цінніші мінімум залежностей і продовження чинного smoke setup.
Лише через нестабільність `t.mock.module()` міняти runner я б не рекомендував.
Жодних тестів, конфігурацій чи залежностей цього разу не змінював.

Джерела: [Node.js v24.13.1 test runner](https://nodejs.org/docs/v24.13.1/api/test.html),
[Vitest mocking](https://vitest.dev/guide/mocking) і
[Stryker TAP runner](https://stryker-mutator.io/docs/stryker-js/tap-runner/).

## Користувач — обговорення повного завдання та узгодження спеки

Тепер перейдемо до повного завдання. Поки що не починай реалізовувати тести. Спочатку обговоримо його: якщо треба якісь уточнення - питай, а після цього напишемо спек.
Потрібно зробити:
юніт тести - достатньо лише одного модуля, але покритого повністю (усі йог гілки). Модуль не повинен бути дуже великим - думаю carriers підійде;
інтеграційні тести - треба перевірити взаємодію компонентів з піднятими залежностями, особливо postgres. Важливо перевірити репозиторії, транзакції та їх відкати, ідемпотентність.
E2E - треба перевірити повні сценарії через api із запущеним застосунком. Перевіряти треба поведінку системи від початкового запиту до кінцевого результату.
І інтеграційні і е2е тести повинні використовувати справжню тестову PostgreSQL, а не mock замість БД.

Щодо структури цих типів тестів:
Юніт розміщуй поруч із класами - так як рекомендує офіційна документації Nest, передивись її.
Інтеграційні та е2е - в папці tests в відповідних папках - /integration та /e2e
Також посортуй відповідно тести які вже існують в папці tests

Для цих тестів треба зробити одну команду make test - вона має підняти postgres через docker compose, застосувати міграції та запустити всі три види тестів.


Також потрібно зробити мутаційне тестування. Використовуєм Stryker із vitest ранером - як і обговорювалось. Мутаційне тестування хай доторкається лише критичної логіки - щоб тести не виконувались дуже довго.
Для цього тестування треба буде зробити звіт, в якому обов'язково треба класифікувати вижилих мутантів: реальна прогалина / еквівалентний / прийнятний. Це можна зробити в окремому файлі в docs.

В кінці роботи (але це раз не починай його робити сам без команди) треба зробити аудит. В ньому топ-3, де «зелені» тести не ловлять реальні баги. Якщо такі знайдуться їх треба буде посилити.

## Асистент — первинне обговорення та уточнення

Офіційна документація NestJS рекомендує розміщувати unit-тести поруч із класами та використовувати суфікс `.spec` або `.test`; у прикладах Nest використано `.spec.ts` ([NestJS Testing](https://docs.nestjs.com/fundamentals/testing)). У репозиторії наявні тести поки що в корені `tests/`; інтеграційний тест уже використовує справжню `autobusua_test` і має guard на ім'я БД, а smoke-тест запускає зібраний застосунок окремим процесом. Скрипт міграцій читає `.env`, тому новий `make test` має явно та безпечно спрямовувати міграції й тести саме на тестову БД.

Перш ніж формувати спек, потрібно узгодити:

1. Що саме означає «повністю покритий модуль carriers»: усі гілки `CarriersService` чи всі логічні гілки контролера, сервісу й репозиторію? Для 100% branch coverage варто рахувати вихідні логічні гілки, а не синтетичні гілки, які інструментування може приписати декораторам.
2. Які мінімальні E2E-сценарії мають бути обов'язковими? Пропозиція для обговорення: наскрізний шлях від створення/авторизації потрібних ролей через заявку та її розгляд до створення рейсу, пошуку, купівлі, перегляду й скасування квитка; окремо перевірити критичну відмову авторизації. Також потрібно визначити, чи E2E має запускати зібраний застосунок окремим процесом (як поточний smoke-тест) або ініціалізувати Nest-застосунок у процесі тесту.
3. Як `make test` має поводитися з Compose після завершення або помилки: залишати PostgreSQL запущеною для повторного запуску/діагностики чи зупиняти автоматично? Чи достатньо застосувати міграції до виділеної тестової БД без її очищення/пересоздання?
4. Які модулі/файли включити до мутаційного аналізу? Пропозиція — критичні сервіси та idempotency flow; якщо включити SQL-репозиторії/транзакційну реалізацію, Stryker муситиме частіше запускати інтеграційні тести на PostgreSQL і тривалість зросте. Чи має бути мінімальний mutation score, чи достатньо запуску на погодженому наборі та звіту з класифікацією кожного живого мутанта?
5. Підтвердіть, будь ласка, чи unit-покриття має означати 100% усіх логічних гілок погодженого обсягу, а решта модулів — якісні критичні сценарії без загального порога 100%.

Аудит наприкінці залишаю відкладеним до вашої окремої команди. Звіт про мутації пропоную розмістити поруч із наявними аудитами в `docs/audits/`, якщо ви не задасте інше місце.

А так загалом погоджуюсь зі всім:

5. Так.

## Асистент — вибачення, фіксація переваги та підготовка специфікації

Вибач за повторне використання картки з варіантами, попри твоє попереднє прохання. Додав у `standards/verification-checklist.md` окреме постійне правило: не пропонувати варіанти та не аргументувати їх у choice cards; уточнення ставити відкрито, щоб користувач сам сформулював рішення.

Узгоджені рішення для Spec 03:

1. 100% покриття лише логічних гілок `CarriersService`; синтетичні гілки декораторів/інструментування не враховуються. Controller перевіряється E2E, repository — integration із реальною БД.
2. E2E запускає зібраний застосунок окремим процесом і проходить повний сценарій заявки перевізника, створення/пошуку рейсу та купівлі/перегляду/скасування квитка, включно з критичною відмовою авторизації.
3. `make test` залишає Compose запущеним, не видаляє і не пересоздає тестову БД; кожен тест прибирає лише створені ним записи.
4. Stryker із Vitest runner охоплює ключову бізнес-логіку з unit-тестами; мінімальний mutation score не встановлюється, а кожен surviving mutant класифікується та пояснюється.
5. Повне branch coverage потрібне лише для `CarriersService`; для інших компонентів перевіряються критичні сценарії.

Створено `docs/specs/03-testing.md`. Реалізацію тестів і фінальний аудит не розпочато; аудит залишається відкладеним до окремої команди користувача.

## Асистент — перевірка області idempotency key

У `PostgresIdempotencyStore` запис знаходиться за унікальним набором
`(user_id, operation, key_hash)`, і лише після цього порівнюється
`request_hash`. Тому `operation` та request payload впливають на різні частини
ідемпотентності.

- #142 і #214 не є строго еквівалентними: після видалення ID з operation name
  повтор того самого ключа для іншого рейсу/квитка змінюється з окремої
  операції на `409` через інший payload. Це не відтворює чужий результат.
- #143 і #215 еквівалентні: operation name залишається ресурсно-специфічним,
  а відповідні методи не мають інших параметрів запиту, тож прибраний ID не
  змінює результат хешування для одного operation.

Spec 02 вимагає `409` для іншого payload, але не визначає, чи повторне
використання ключа для іншого рейсу або квитка має бути окремою операцією.
Тому звіт класифікує #142 і #214 як прийнятні, але не еквівалентні, і фіксує
цю невизначену область контракту. Тести перевіряють зміну payload у межах
одного operation, але не ключ, повторно використаний для іншого ресурсу.
Production-код і тести не змінювалися.
