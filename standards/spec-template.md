# Specification Template

Універсальний шаблон для всіх лабораторних робіт. Специфікацію заповнює асистент на основі промптів, стану проєкту та погоджених рішень.

## Правила

- Один документ описує одну лабораторну або одну логічно завершену зміну.
- Документ фіксує очікуваний результат, а не покрокову реалізацію коду.
- Необов'язкові секції залишаються порожніми або містять `N/A` з коротким поясненням.
- Неоднозначності, припущення та рішення не приховуються.
- Кожен критерій приймання має бути перевірюваним.
- Історія обговорення та вибору рішень зберігається в `ai/`.
- Орієнтовний максимальний обсяг заповненої специфікації: 6–7 тисяч символів.

## Template

```markdown
# Spec NN

## Назва специфікації

## Context
### Current State
Поточний стан системи, репозиторію та документації.

### Problem
Проблема або потреба, яку вирішує ця ітерація.

## Goal
Мета роботи та очікуваний результат.

## Scope
### In scope
- Що входить у роботу.

### Out of scope
- Що свідомо не входить у роботу.

## Implementation
Що було зроблено в межах роботи: реалізовані налаштування, структура,
документація, технічні рішення та пов'язані ADR. Для лабораторних, де
імплементація не потрібна, зазначити `N/A`.

## Acceptance Criteria
- **AC-1:** За умови ..., після дії ... система повинна ...

Кожен критерій має бути одним перевірюваним реченням і покривати позитивні,
негативні та граничні сценарії, якщо вони належать до scope.

## Verification
Як перевіряється результат: команди, автоматизовані тести, ручні сценарії,
перевірки міграцій, конкурентності, безпеки, збірки та продуктивності.
Посилатися на `standards/verification-checklist.md`, коли це доречно.

## Open Questions
- [ ] Невирішене питання або припущення.
```

## Вимоги до заповнення

- `Context` не дублює всю історію проєкту, а містить лише релевантний стан.
- `Scope` явно захищає від розширення роботи.
- `Implementation` описує фактично виконану роботу, а не майбутню реалізацію.
- `Acceptance Criteria` не містять слів «правильно», «зручно» чи «швидко» без
  вимірюваної умови.
- Для простих сценаріїв достатньо одного рядка; формат `Given / When / Then`
  можна використовувати лише коли критерій стає неоднозначним або складним.
- Для доступу вказуються роль, ресурс, дія та очікувана відмова.
- Для конкурентності вказуються кількість паралельних операцій і допустимий
  результат.
- `Verification` містить конкретний спосіб перевірки, а не загальну заяву
  «протестувати».
- Після узгодження всі порожні `Open Questions` мають бути закриті або явно
  прийняті як припущення.
